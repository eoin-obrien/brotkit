# Spike S4: register pressure, resource reporting, compiling without a GPU

- **Date:** 2026-11-24
- **Machine:** Xenon (WSL2, RTX 3090 Ti, compute capability 8.6, 24 GB VRAM; the desktop and
  local LLM inference share the card)
- **Backlog:** S4 ([#10](https://github.com/eoin-obrien/brotkit/issues/10)), the second half of
  the [ADR-0005](../decisions.md) backend gate
- **Code:** [`spikes/S4_registers/`](../../../spikes/S4_registers/) (throwaway). Library code
  that came out of it: `brotkit.backends.resources`, `brotkit.backends.cuda.resource_usage`,
  `brotkit.codegen.checks.find_bare_float_ops`.
- **Outcome:** the gate **passes**. No tier spills at default settings, for any kernel up to six
  fused features, on sm_86, sm_100 or sm_120. Resource reporting works and matches the driver
  exactly. **Q1 fails as shipped:** numba-cuda-mlir 0.6.0 needs a CUDA driver and a device to
  run `compile_ptx`, even for an explicit compute capability, so CPU CI gets no compile-only
  check yet. Proposed as [ADR-0007](../decisions.md).

## Summary

| Question | Answer |
| --- | --- |
| **Q1** Compile to PTX for a given cc with no GPU or driver? | **No** on numba-cuda-mlir 0.6.0. Every `cuda.compile_ptx(..., cc=...)` raises `CudaSupportError` at driver init, both in a container with no driver and on the host with `CUDA_VISIBLE_DEVICES=""`. Two host-cc lookups inside numba-cuda-mlir cause it. Everything after PTX (ptxas, nvJitLink, cuobjdump, nvdisasm from the wheels) works offline. Upstream issue drafted, not filed. |
| **Q2** Reliable resource reporting? | **Yes.** `resource_usage(kernel, signature, cc)` compiles to PTX and links it with nvJitLink (`-verbose -Xptxas=-v`), the linker the dispatcher uses. It matched the driver in **175/175** configurations: registers, local memory, shared memory, max threads per block, and blocks/SM at 128 and 256. Standalone `ptxas -v` is wrong in 18 of 35 kernels (up to 7 registers under). |
| **Q3** Register pressure by tier | f32 20–44, f64 25–52, df64 28–54, dd 40–72, qf 47–72 registers (1 to 6 features, sm_86). **Zero spills everywhere** at default settings. The only local memory is 32 B from libdevice `sinf` (stripe average). |
| **Q4** Caps | Capping below the default allocation never helped. Spill-free caps ranged from neutral to −5%; caps that force spills cost 2–70%. A loose cap (`max_registers=128`) makes ptxas use *more* registers than the default and speeds qf up 12% (kernel C) and dd 5%. `max_registers` applies per kernel and works on both MLIR paths. |
| **Split threshold** | **None up to six features**, for single-word and multi-word tiers alike. The fused 6-feature kernel never spills and is always faster than the split 3 + 3 passes (by 13–17% for f32, 28–71% for the others). |
| **qf vs dd** | qf is **9–12× faster than dd** on this card (10.8 vs 1.05 Giter/s on kernel C), with error within 4 u = 2⁻⁹⁴ on every composite op. |

**Gate verdict: PASS.**

- f32, df64 and f64 run A–C with zero spills at default settings.
- dd and qf run C with zero spills at default settings, so no cap is needed and the 15% rule
  doesn't come into play.
- Q2 works.

Q1, reported separately, fails, so the CI plan changes: the PTX snapshot and resource tests are
marked `gpu`.

## Kernels and tiers

`gen.py` emits each kernel as Python source, the same way the real codegen will. Every kernel
iterates z² + c over a 2D grid and writes the S3 layer layout (7 float layers, 3 uint layers).

| Kernel | Features (accumulators fused into the loop) | Count |
| --- | --- | --- |
| Z | none: escape loop only, no finaliser (used for the PTX checks) | 0 |
| A | smooth | 1 |
| B | smooth + distance estimate | 2 |
| C | smooth + DE + orbit trap (point) | 3 |
| F6 | C + stripe average + triangle inequality average + binary decomposition | 6 |
| S2 | stripe + TIA + binary: the second pass of a split | 3 |

| Tier | Words | Arithmetic |
| --- | --- | --- |
| f32 | 1 × float32 | bare operators (contracted, as the f32 baseline would be) |
| f32rn | 1 × float32 | `_rn` intrinsics (one extra data point, kernel A) |
| f64 | 1 × float64 | bare operators |
| df64 | 2 × float32 | S3's df64, `_rn` intrinsics + `cuda.fma` (ADR-0006) |
| dd | 2 × float64 | S3's dd, likewise |
| qf | 4 × float32 | new prototype: QD-library sloppy add, mul and sqr with the branch-free renormalisation |
| qfb | 4 × float32 | the same qf with QD's branchy renormalisation (for comparison) |

Accumulators are float32, fed from the high word. Bailout radius² is 1e12 (1e6 for plain f32).
All multi-word kernels compile with `fastmath=False`.

## Q1: compiling with no GPU

`q1_nogpu.py` tries each call and records the result in `results/q1_<label>.json`. It ran
in four settings:

| Call | No-driver container | Host, `CUDA_VISIBLE_DEVICES=""` | Container + host-cc stub (diagnostic) | GPU host |
| --- | --- | --- | --- | --- |
| `import numba_cuda_mlir.cuda` | ok | ok | ok | ok |
| `cuda.compile_ptx(f, sig, cc=(8,6))`, also `(10,0)`, `(12,0)` | **CudaSupportError** ("CUDA driver library cannot be found") | **CudaSupportError** (`CUDA_ERROR_NO_DEVICE`) | ok for f32 and dd; qf fails ("Invalid compute capability: sm_00") | ok |
| `compile_ptx(..., launch_bounds=(256, 2))` | fails | fails | ok | ok |
| `compile_ptx(..., cc=None)` | fails | fails | fails (no device by design) | ok |
| `cuda.compile(..., output="ltoir")` for a kernel | NotImplementedError ("The C ABI is not supported for kernels") | same | same | same |
| `cuda.compile(..., output="cubin")` | NotImplementedError ("Unsupported output type") | same | same | same |
| wheel `ptxas -v [-maxrregcount=N]` on PTX | ok (given PTX) | ok | ok | ok |
| nvJitLink `-verbose -Xptxas=-v [-maxrregcount=N]` | ok (given PTX) | ok | ok | ok |
| wheel `cuobjdump --dump-resource-usage`, `nvdisasm` | ok (given a cubin) | ok | ok | ok |
| `cuda.jit(chip="sm_86")` + `.compile(sig)` + `inspect_asm` | fails | fails | ok | ok |
| `dispatcher.get_regs_per_thread()` and the other getters | fails | fails | fails (`cuFuncGetAttribute` needs a device) | ok |
| `brotkit.backends.cuda.resource_usage` | fails (via `compile_ptx`) | fails | ok for f32 and dd | ok |

**Cause.** `numba_cuda_mlir/tools.py:43 resolve_gpu_target` calls
`get_gpu_compute_capability()` unconditionally, even when `chip` is given, and that creates a
context. A second site, `mlir_compiler.py:315`, re-resolves the target for device functions
compiled as separate callees, and their target options don't carry the caller's `chip`. qf
hits this site and f32/dd don't. With both lookups stubbed out, the whole chain from Python
source to cubin to resource numbers runs with no GPU. The upstream issue
(`spikes/S4_registers/upstream_issue.md`) proposes a lazy lookup and passing `chip` through
to callees.

**Consequence.** No compile-only CPU CI check yet. `tests/test_cuda_ptx.py` holds the PTX
snapshot and resource tests and is marked `gpu`. Its docstring says to drop the marker once
upstream fixes the lookup, but to keep the dispatcher comparison GPU-only. CPU CI still runs
the source-level checker (below) and the pure-Python occupancy tests.

## Q2: reading registers, spills, memory and occupancy

`q2_compare.py` read every kernel (7 tiers × 5 kernels, sm_86) four ways:

| Source | Registers equal the driver's | Notes |
| --- | --- | --- |
| Driver (`cuFuncGetAttribute` via the dispatcher getters) | reference | needs a GPU |
| Standalone `ptxas -v` on `compile_ptx` output | 17/35 | Reports the entry function only. It is off in 18 kernels: under by 1–7 registers in 16, where the SASS `CALL`s subroutines (the IEEE div/sqrt slow paths in B and C, libdevice trig in F6 and S2), and over by 1–3 in 2 (dd/B, qfb/F6). |
| nvJitLink, `-verbose -Xptxas=-v` on `compile_ptx` output | **35/35** | Its final `used N registers, N stack, N bytes smem` line is whole-program. `stack` equals the driver's local memory. |
| ptxas on the dispatcher's LTO PTX | 17/35 | the same numbers as standalone |

`resource_usage` is the nvJitLink route. It returns a frozen `ResourceUsage` (registers, spill
store/load bytes summed over every function, stack bytes, static shared bytes, max threads per
block, the cap it was built under). `occupancy(usage, block_size)` is pure Python with the
arithmetic of `cuda_occupancy.h`: registers are allocated per warp in units of 256 from four
sub-partitions, and the runtime reserves 1 KB of shared memory per block. Per-arch limits are
tabulated for sm_80, 86, 89, 90, 100 and 120.

`q2_validate.py` compared `resource_usage` + `occupancy` with the driver, including
`cuOccupancyMaxActiveBlocksPerMultiprocessor`, for 35 kernels × caps {none, 32, 64, 96, 128}:
**175/175 match** on registers, local memory, shared memory, max threads per block and blocks per
SM at 128 and 256. Two cases show why the per-partition rule matters: 77 registers give 768
threads per block (not 800), and 66–72 registers give 896.

Two pitfalls, both handled in `brotkit.backends.cuda.link_info`:

- **nvJitLink's compute cache hides the spill lines.** nvJitLink caches ptxas results in
  `~/.nv/ComputeCache`. On a hit, the verbose log keeps the summary but drops the ptxas block
  that carries `bytes spill stores/loads`. `CUDA_CACHE_DISABLE` is read only when the library
  loads. brotkit appends a unique comment to the PTX before linking, and
  `parse_nvjitlink_log` refuses a log without spill lines rather than reporting zero.
- The log ends in a NUL, as `compile_ptx` output does.

`resource_usage` takes a signature string or a sequence of types. numba-cuda-mlir's
`compile_ptx` iterates a string as if it were a type list, so `signature_args` parses strings
first.

## Q3: register pressure and throughput

Method (`q3_throughput.py`):

- 3840 × 2160, max_iter 1000, S3's seahorse view (centre −0.743643887037151 + 0.131825904205330i,
  width 0.05). The mean escape count is 437, the same for every tier.
- Giter/s = Σ escape counts / kernel time. Launches are split into row bands of about 0.25 s
  (the WDDM watchdog).
- Each config: compile, one full warm-up render, a spin of at least 1 s to reach boost clock,
  then the **median of 5** timed renders. A render under 0.2 s is repeated and averaged.
- A sampler thread records SM clock and temperature every 100 ms. Within every config the
  clock varied by under 5%, so none were flagged.
- **Before every config, the GPU is checked**: the median of 8 utilisation samples over 1.2 s
  must be ≤ 5%, and memory must not have grown more than 1.5 GiB. If the check fails, the
  script waits 20 s and checks again; nothing is measured meanwhile. The Windows desktop
  compositor shows 1–40% bursts at the 210 MHz idle clock with no compute process. The rule
  started as "any sample > 5%", but that paused the run every few configs, so the maintainer
  agreed to the median rule and then to waiting out bursts. 3 configs in the cap sweep waited.

### Readings

- **Spills: none.** The highest count is 72 registers (dd and qf with 6 features) on all three
  architectures, well short of 255.
- **Local memory is not spilling.** The 32 B in F6/S2 is libdevice `sinf`'s large-argument
  reduction array (stripe average), which also brings one `mul.f64` into f32 kernels. qfb's
  112–240 B comes from QD's branchy renormalisation. It returns tuples through stack slots with
  pointer selects, which puts `st.local`/`ld.local` in the hot loop. The branch-free
  renormalisation (qf) removes all of it and runs 1.66× faster (10.82 vs 6.53 Giter/s on C at
  the same 0.5–0.667 occupancy). qfb also ran ~7% below the usual boost clock.
- **Features cost compute, not occupancy.**
  - On f32, F6 runs 4.4× slower than C (119.5 vs 522.9 Giter/s) while occupancy drops only
    from 1.0 to 0.83. The cost is the `atan2` + `sinf` in stripe average (S2 alone is 133
    Giter/s).
  - On dd, F6 is as fast as C. dd is bound by the card's 1:64 FP64 rate, and the extra
    float32 accumulators hide behind it.
  - DE (A → B) is the costly feature for the multi-word tiers: −56% for dd and qf, −50% for
    df64. Its derivative is a full complex multiply per iteration.
- **f32 with `_rn` intrinsics** (kernel A) reaches 924–951 Giter/s against 964–998 for
  contracted bare operators: 4–5% slower, at the same 20 registers.
- **sm_100's occupancy fractions are lower** at the same register count because it has 64
  warps/SM against 48. The absolute number of resident warps is the same or higher.

### Split threshold: fused F6 against C + S2

| Tier | Block | F6 fused (s) | C + S2 split (s) | Split / fused | Fused spills? |
| --- | --- | --- | --- | --- | --- |
| f32 | 128 | 0.0296 | 0.0346 | 1.17 | no |
| f32 | 256 | 0.0303 | 0.0341 | 1.13 | no |
| df64 | 128 | 0.0696 | 0.0948 | 1.36 | no |
| df64 | 256 | 0.0759 | 0.0968 | 1.28 | no |
| f64 | 128 | 0.306 | 0.466 | 1.52 | no |
| f64 | 256 | 0.286 | 0.466 | 1.63 | no |
| dd | 128 | 3.086 | 4.846 | 1.57 | no |
| dd | 256 | 3.189 | 5.460 | 1.71 | no |
| qf | 128 | 0.336 | 0.478 | 1.42 | no |
| qf | 256 | 0.349 | 0.511 | 1.46 | no |

The split pays for the escape loop twice. Each pass re-iterates z² + c, which is the expensive
part in every multi-word tier. Splitting would have to save more occupancy than that, and with
no spills it never does.

**Split threshold: the fused kernel neither spilled nor lost to the split at any feature count
up to 6. That holds for single-word tiers (f32, f64) and multi-word tiers (df64, dd, qf). The
threshold is above 6 for both.** Recommendation for the spec: don't split on a feature count or
a register count. Split only when `resource_usage` reports spills at the default build. Then
check the split is faster, because a split re-runs the escape loop.

**qf beat dd by 9.1–12.4×** on this 1:64-FP64 card, at a similar register count (47–72 vs

relative to qf, which is why the spec has `Precision.AUTO` benchmark per device.

qf correctness (`q3_qf_exact.py`, `q3_deep_mismatch.py`):

- **Error-free primitives** (S3's `eftcheck` groups, about 1.2M inputs each): `two_sum`,
  `quick_two_sum` and in-domain `two_prod` have **0 failures**.
- **Composite ops** against mpmath, in u = 2⁻⁹⁶, 200,000 inputs each:

  | Op | Max error (u) |
  | --- | --- |
  | add | 0.124 |
  | add with cancellation | 0.125 |
  | mul | 3.74 |
  | sqr | 1.33 |
  | complex mul | 3.06 |

  None is over 16 u. qf and qfb give identical numbers.
- **Deep render** at pixel spacing 1e-20 around M(4,1): qf matches dd on 4092/4096 pixels.
  - At three of the four differing pixels, qf matches mpmath evaluated at qf's own c. The
    difference is in c, not the iteration. The pixel offset is formed as one float32 product
    (`fmul_rn(ox, dx)`).
  - The fourth is the centre pixel, a Misiurewicz point, where both tiers disagree with
    mpmath, as expected.
  - Fix for the real printer: form the pixel offset in full qf precision.
- **Caveat, not measured:** qf has float32's exponent range. A DE derivative carried in the high
  word can overflow at 3.4e38 on deep zooms, so the real qf printer needs a rescaled or
  extended-exponent derivative.

## Q4: register caps

Mechanics (`probe_caps.py`, `results/q4_mechanics.json`):

- **The cap applies per kernel.** Two dispatchers from one module, one with
  `max_registers=24`, give 24 and 30 registers.
- **It survives both MLIR paths.** The LLVM-7 bridge below sm_100 honours `max_registers`, and
  so does the modern path: `chip="sm_100"` / `"sm_120"` with `max_registers=48` gives a cubin
  with `REG:48` (71–72 uncapped). numba-cuda-mlir passes it to nvJitLink as `-maxrregcount` at
  link time.
- **`launch_bounds` reaches the PTX** as `.maxntid` / `.minnctapersm` at all three ccs and
  steers ptxas the same way.
- **Bug: `cache=True` ignores `max_registers`.** The cache key leaves it out, so an uncapped
  dispatcher loaded a 24-register capped build from cache.

Readings:

- **Without `-maxrregcount`, ptxas does not use as many registers as it could.** With a loose
  cap it takes more, accepts lower occupancy and runs faster: qf/C goes from 64 to 117
  registers, occupancy from 0.667 to 0.333, throughput +12%; dd/C +5%. These kernels are
  latency-bound on dependent multi-word chains, where more registers per thread beat more
  warps.
- **Capping for occupancy never paid off.** Spill-free caps were neutral; caps that forced
  spills cost 3% (dd/F6 at 64), 26% (df64/F6 at 32) and up to 70% (qf/F6 at 32). Forcing
  occupancy to 1.0 at 32 registers was always slower. dd/C at 32 only broke even, because dd
  is bound by FP64 throughput and hides the spill traffic.
- The cap was never needed to avoid spills, so the gate's 15% rule didn't come into play.

**Recommended caps** (sm_86; re-check on other architectures with `resource_usage` and a timing):

| Tier | Cap | Why |
| --- | --- | --- |
| f32 | none | ≤ 45 registers, occupancy ≥ 0.83; caps changed nothing |
| df64 | none | caps were neutral or worse; a forced spill at 32 costs 26% |
| f64 | none | identical SASS under every loose cap; differences are noise |
| dd | none (optionally 128: +5%) | no spills at default; 128 measured +5%, inside the run-to-run noise but steady in the interleaved repeat |
| qf | **128** | +12% on C, +2% on F6, no spills; never cap below the default |

Never set a cap below a kernel's default register count. Until upstream fixes the cache key,
don't combine `cache=True` with a varying `max_registers`.

## GPU-free CI checks

### Source checker: `brotkit.codegen.checks.find_bare_float_ops`

This is an AST heuristic for ADR-0006. In multi-word source, `+`, `-` and `*` (and `+=` etc.)
are allowed only:

- inside subscript slices;
- inside `range()` arguments;
- when every operand is an int literal or a name on an explicit allowlist that the printer
  passes in (S4: `x y yy w h n row0 max_iter trap_n bits`).

Everything else is reported with line, column, function and source text. The checker can't see
types, so the PTX check is authoritative.

- CPU tests (`tests/test_codegen_checks.py`) cover unit cases, Hypothesis properties, negative
  tests, rn fixtures (clean) and naive or plain fixtures (flagged).
- Over every S4 module (`check_codegen.py`), it gives **0 findings** on all df64, dd, qf and
  qfb kernels, and flags every control (plain f32/f64, naive dd/qf).

### PTX checks: `tests/test_cuda_ptx.py` (marked `gpu` because of Q1)

20 tests, all passing on Xenon:

- **f32 kernels A–C contain no `.f64` instruction** at sm_86, sm_100 and sm_120. This catches
  the int64 × float32 → float64 promotion from S3. F6/S2 are excluded because libdevice `sinf`
  legitimately uses one `mul.f64`.
- **The multi-word core (kernel Z) is rounding-explicit** at all three ccs:
  - no un-rounded `add`/`sub`/`mul`, and no `mad`;
  - every `fma` is `.rn` without `.ftz`;
  - the FMA count in the kernel entry equals the explicit `cuda.fma` sites after inlining:
    3 for df64 and dd, 14 for qf.

  numba-cuda-mlir also leaves uncalled `.func` copies of qf's `w_sqr`/`w_mul` in the PTX (10
  more FMAs), so the count is taken over the `.entry` body only.
- **`resource_usage` equals the dispatcher's getters** (registers, local, shared, max threads)
  for dd and qf at caps none/32/48.

Not added: a workflow change. Per the maintainer, label-gated GPU runs on the self-hosted runner
wait for 0.3 and their own security review. Untrusted PR code never runs there.

## Recommendations

1. **Adopt `resource_usage` as the single source of resource numbers** (ADR-0007). It needs no
   device beyond what `compile_ptx` currently needs, it matches the driver, and it reports
   spills, which the driver doesn't.
2. **Fuse by default and split only on spills.** Change spec architecture-review item 3 from
   "above a threshold, split" to "split only when `resource_usage` reports spills at the
   default build, and only if the split pass is faster". S4 found no spilling kernel up to 6
   features in any tier. The maintainer mirrors this into the spec.
3. **qf is worth building** (backlog phase 2): 9–12× dd on consumer cards, accurate to under
   4 u. Use the branch-free renormalisation (the branchy one costs 40% through local memory),
   form pixel offsets in qf precision, and handle DE's exponent range. Start qf at
   `max_registers=128`.
4. **CI:** keep the PTX and resource tests `gpu`-marked until upstream fixes the host-cc lookup.
   Then move the PTX snapshot tests to hosted CI. Run the AST checker on every generated
   multi-word source in CPU CI from backlog 1.3.
5. **Costs to know about for later features:** stripe average's `atan2` + `sinf` dominates f32
   F6 (4.4× slower than C); DE halves multi-word throughput. Both are compute, not registers.
6. **Benchmark hygiene on Xenon:** the desktop compositor causes ±10% drift between runs. For
   any A/B decision, interleave the variants in one process, as `q4_repeat.py` does, rather
   than compare separate runs.
