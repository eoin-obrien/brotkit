# Spike S1: CUDA install on WSL2

- **Date:** 2026-11-23
- **Machine:** Xenon (WSL2, RTX 3090 Ti, 24 GB VRAM shared with local LLM inference)
- **Backlog:** S1 ([#7](https://github.com/eoin-obrien/brotkit/issues/7))
- **Code:** [`spikes/S1_install/`](../../../spikes/S1_install/) (throwaway)
- **Outcome:** passes on Python 3.14 and 3.15, using **`numba-cuda-mlir`** instead of
  `numba-cuda`. That's a change of GPU JIT, recorded as [ADR-0005](../decisions.md).

## Summary

`numba-cuda` has no CPython 3.15 wheels and never will: NVIDIA put it in maintenance mode and
closed both the 3.15 and the NumPy 2.5 requests, pointing users to `numba-cuda-mlir`. On 3.14,
`numba-cuda` 0.30.4 works only with `numpy<2.5`. `numba-cuda-mlir[cu13]` 0.6.0 ran the same
smoke test on 3.14.0 and 3.15.2 with NumPy 2.5.5, wrote its on-disk cache and reloaded it in a
fresh process, and works alongside CPU `numba` 0.68.1 in one process. The `[cuda]` extra is now
`numba-cuda-mlir[cu13]==0.6.0`.

## Packages that install via uv

### Chosen: `numba-cuda-mlir[cu13]==0.6.0`

Identical on 3.14 and 3.15 (from `uv sync --group dev --extra cuda` in the brotkit project):

| Wheel | Version | Role |
| --- | --- | --- |
| `numba-cuda-mlir` | 0.6.0 | GPU JIT (cp311–cp315 wheels, no sdist). No `numba`/`llvmlite` dependency |
| `cuda-toolkit` | 13.5.0 | Metapackage, extras `cudart,nvcc,nvrtc` |
| `nvidia-cuda-runtime` | 13.5.37 | `libcudart.so.13` |
| `nvidia-cuda-nvcc` | 13.5.37 | nvcc components |
| `nvidia-cuda-crt` | 13.5.37 | CUDA C runtime headers |
| `nvidia-cuda-nvrtc` | 13.5.37 | `libnvrtc.so.13` |
| `nvidia-nvvm` | 13.5.37 | `libnvvm.so.4`, libdevice |
| `nvidia-nvjitlink` | 13.5.37 | `libnvJitLink.so.13` |
| `cuda-bindings` | 13.5.0 | Python bindings to driver/runtime/NVRTC |
| `cuda-core` | 1.3.1 | |
| `cuda-pathfinder` | 1.9.1 | Locates the libraries above |
| `numpy` | 2.5.5 | Unconstrained by the GPU stack |

All wheel libraries land under `site-packages/nvidia/cu13/`. `cuda-pathfinder` reported
`found_via=site-packages` for nvrtc, nvJitLink, cudart and nvvm, even though CUDA 12.9 is
installed system-wide, so the wheels take priority over `/usr/local/cuda`.

### Fallback only: `numba-cuda[cu13]==0.30.4` (3.14)

`numba` 0.68.1, `llvmlite` 0.50.0, `cuda-toolkit[cccl,cudart,nvrtc,nvvm]` 13.5.0 (same
`nvidia-*` 13.5.37 wheels as above, plus `nvidia-cuda-cccl` 13.3.5.0.6 and minus nvcc/crt),
`cuda-bindings` 13.5.0, `cuda-core` 1.3.1, `cuda-pathfinder` 1.9.1, and **`numpy` 2.4.6** (held
below 2.5). Lock: `spikes/S1_install/uv.lock`.

### cu13 vs cu12

cu13 worked first time, so cu12 wasn't tried. The driver supports CUDA 13 (numba-cuda-mlir
needs r580+ for CUDA 13), and CC 8.6 is still supported by CUDA 13. The 13.5 runtime/NVRTC
wheels run on a driver reporting 13.3, through CUDA minor-version compatibility. That gap
(runtime newer than driver) is worth showing in `brotkit doctor`. A future 13.x wheel could
emit PTX the driver's JIT doesn't accept.

## Commands and results

```bash
uv self update                                           # 0.9.10 -> 0.13.9
uv python install 3.15                                   # 3.15.2

# numba-cuda (fallback)
cd spikes/S1_install
uv sync -p 3.14 && uv run smoke.py                       # FAIL with numpy 2.5.5, PASS with numpy<2.5
uv sync -p 3.15                                          # FAIL: no cp315 wheel

# numba-cuda-mlir (chosen), standalone
cd spikes/S1_install/mlir
uv sync -p 3.15 && S1_BACKEND=mlir uv run --project . python ../smoke.py   # PASS (x2)
S1_BACKEND=mlir uv run --no-project --isolated -p 3.14 \
  --with "numba-cuda-mlir[cu13]==0.6.0" --with numpy python ../smoke.py     # PASS

# numba-cuda-mlir from the brotkit project (the acceptance command)
uv sync --group dev --extra cuda                          # 3.14, repo .venv
S1_BACKEND=mlir uv run python spikes/S1_install/smoke.py  # PASS
UV_PROJECT_ENVIRONMENT=<scratch> uv sync -p 3.15 --group dev --extra cuda
UV_PROJECT_ENVIRONMENT=<scratch> S1_BACKEND=mlir uv run -p 3.15 python spikes/S1_install/smoke.py  # PASS
```

`smoke.py` checks free VRAM, prints versions and device facts, and runs three kernels on
2^18 elements, checking each against NumPy: f32 `a*x + y`, an f64 sum with
`cuda.atomic.add`, and an f32 kernel with `cache=True`.

| Run | Python | Import | f32 compile+run | f64 atomic | `cache=True` kernel | Result |
| --- | --- | --- | --- | --- | --- | --- |
| numba-cuda 0.30.4, numpy 2.5.5 | 3.14.0 | n/a | `AttributeError: module 'numpy' has no attribute 'row_stack'` at first compile | | | FAIL |
| numba-cuda 0.30.4, numpy 2.4.6 | 3.14.0 | 0.77 s | 0.35 s | 0.03 s | miss 0.03 s, then hit 0.00 s | PASS |
| numba-cuda 0.30.4 | 3.15.2 | uv: "only has wheels with the following Python ABI tag: `cp314`" | | | | FAIL (install) |
| numba-cuda-mlir 0.6.0, cold | 3.15.2 | 2.04 s | 1.09 s | 0.06 s | miss 0.06 s | PASS |
| numba-cuda-mlir 0.6.0, warm | 3.15.2 | 0.60 s | 0.38 s | 0.04 s | **hit** 0.00 s | PASS |

S2 measures cold/warm times properly.

`numba-cuda-mlir` and CPU `numba` 0.68.1 in one 3.15 process: an `@njit(parallel=True)`
reduction and an mlir `@cuda.jit` kernel both gave correct results. `numba.cuda` (numba's own
deprecated target) still exists in 0.68.1 and doesn't conflict.

## On-disk cache (input to S2)

- **Default location:** a `__pycache__/` directory next to the source file that defines the
  kernel, with files `<module>.<function>-<lineno>.py3XX.nbi` (index) and
  `<module>.<function>-<lineno>.py3XX.<n>.nbc` (data). For example
  `spikes/S1_install/__pycache__/smoke.cached_kernel-81.py315.1.nbc`. The tag includes the
  Python minor version, so 3.14 and 3.15 entries sit side by side.
- **`NUMBA_CACHE_DIR` is honoured** by numba-cuda-mlir: files go to
  `$NUMBA_CACHE_DIR/<parent-dir>_<sha1>/<same names>`. brotkit can point this under
  `~/.cache/brotkit/`.
- **`cache=True` works from the standalone spike project:** index and data were saved on the
  first run and loaded (`index loaded from …`, `data loaded from …`, `cache_hits=1`) in a
  fresh process. Same behaviour on numba-cuda 0.30.4.
- `NUMBA_DEBUG_CACHE=1` prints every save and load. This works on both packages.
- Under WSL2 the cache sits on the Linux ext4 filesystem, not `/mnt/c`. Keep it there; DrvFs
  is slow for many small files. The root disk is **97% full (13 GB free)**, and a CUDA venv
  is about 1.1 GB (575 MB of it NVIDIA wheels), so expect disk-space trouble here before
  anything CUDA-related fails.

## Findings beyond the criteria

1. **No CUDA simulator in numba-cuda-mlir.** `NUMBA_ENABLE_CUDASIM=1` is ignored (the kernel
   ran on the real GPU), the package has no simulator module, and upstream has no issue
   about one. Decided in review: CPU CI runs codegen snapshot tests and CPU-backend parity
   tests, and GPU coverage comes from the self-hosted runner (nightly, before releases, and on
   PRs the maintainer labels `gpu`; never untrusted code). S4 checks whether PTX compiles
   without a GPU, which would allow a compile-only CPU CI check. Recorded in ADR-0005, the
   spec and the 0.3 issue.
2. **System toolkit ignored.** The spec said "a system toolkit is used if present and newer".
   In practice `cuda-pathfinder` picks the wheels first. Spec updated.
3. **Pre-1.0 dependency.** numba-cuda-mlir is at 0.6.0, and its
   extension API differs from numba-cuda's (MLIR, not LLVM IR). That's handled by the exact
   pin, no Dependabot auto-merge, and the nightly GPU gate.
4. **Not yet verified on numba-cuda-mlir** (these become S3/S4 gate conditions): `fastmath`
   semantics, PTX inspection, register counts and occupancy reporting, and the
   per-compute-capability cache keying that the spec cites from numba-cuda docs.

## Items for `brotkit doctor` (1.20)

- Driver CUDA version (`cuDriverGetVersion`) vs runtime (`cudaRuntimeGetVersion`) and NVRTC
  version. Warn when the runtime is newer than the driver (13.5 on 13.3 here works now, but
  it's the first thing to check on a PTX JIT error).
- Library paths and `found_via` from `cuda.pathfinder.load_nvidia_dynamic_lib` for nvrtc,
  nvJitLink, cudart and nvvm, so a stray system toolkit is easy to spot.
- Device name, compute capability, `SINGLE_TO_DOUBLE_PRECISION_PERF_RATIO`, and free VRAM
  (from `nvidia-smi` or the driver). Under WSL2, per-process usage isn't available, so say so.
- The effective kernel cache directory (`NUMBA_CACHE_DIR`, or brotkit's default).
- Python version and the `numba-cuda-mlir` version. Run a smoke kernel like `smoke.py`.
- The 3.15 error path from the original plan isn't needed now that numba-cuda-mlir supports
  3.15. If the ADR-0005 fallback is ever revived, doctor and the CUDA backend must raise a
  clear "numba-cuda has no CPython 3.15 wheels; use Python 3.14 for GPU work" instead of
  failing silently behind a `python_version` marker.

## Spec changes (made in this PR, mirror into the master design doc)

- Toolchain decisions: the intro sentence and the **GPU JIT** row now say
  `numba-cuda-mlir[cu13]==0.6.0`, with the maintenance-mode evidence.
- Open questions: the cp315 question is resolved. The `numba-cuda-mlir` question becomes the
  S3/S4 gate.
- **CUDA toolkit install** row: exact wheel names, driver r580+, wheels before the system
  toolkit, minor-version compatibility, and the doctor fields listed above.
- **CI and GPU testing** row: no simulator. CPU CI runs codegen snapshots and CPU parity; GPU runs nightly, before releases and on `gpu`-labelled PRs; a compile-only CPU check if S4 shows PTX compiles without a GPU.
- Architecture review: the caching row notes the S1 cache observation, and the fastmath risk
  notes that S3 must confirm it on numba-cuda-mlir.
- Mentions of `numba-cuda` elsewhere (cache key, provenance, `numba_cuda` → `numba_cuda_mlir`
  metadata field, diagrams, layout, benchmarks, free-threading, references) renamed.
- Backlog: 0.3 (Dependabot gate, simulator decision), S3/S4 (run on numba-cuda-mlir, stop and
  report on failure), 1.4 and 1.20 (doctor fields).
- AGENTS.md invariant 8 and the codegen AGENTS.md: only `backends/cuda.py` imports
  `numba_cuda_mlir`. Ruff `TID251` enforces it (and bans `numba.cuda`).
