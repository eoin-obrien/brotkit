# Spike S2: kernel cache

- **Date:** 2026-11-24
- **Machine:** Xenon (WSL2, RTX 3090 Ti, compute capability 8.6, i9-12900K; the desktop and local
  LLM inference share the card)
- **Backlog:** S2 ([#8](https://github.com/eoin-obrien/brotkit/issues/8))
- **Code:** [`spikes/S2_cache/`](../../../spikes/S2_cache/) (throwaway). Library code that came
  out of it: `brotkit.kernels.cache` (key, store, locking, GPU-free) and
  `brotkit.backends.cuda.CudaCacheBackend` (build and load adapter).
- **Outcome:** the gate **passes**. brotkit stores the nvJitLink cubin itself and loads it with
  `cuda.core`, without Numba, in 13–16 ms per kernel in a fresh process (worst sample 21 ms).
  Kernels move to a raw-pointer ABI with `int64` integers. Recorded as
  [ADR-0008](../decisions.md) (Accepted).

## Summary

| Question | Answer |
| --- | --- |
| **Q1** Cold cost | 0.18 s (f32/A) to 2.51 s (qf/F6) per kernel, from source string to a launched kernel. Numba's frontend (bytecode to MLIR, typing, lowering) is 55–80% of it. Each process also pays a one-time 0.47 s to import numba-cuda-mlir, 0.44 s for cuda.core and the context, and 0.46 s for compiler setup. |
| **Q2** Mechanism | **(b): brotkit stores the cubin and loads it through `cuda.core`**, on public API only, after moving kernels to a raw-pointer ABI. (a) Numba `cache=True` works but serves stale builds for 4 options and for changed constants, unpickles its files, and takes 310–340 ms to load. |
| **Q3** Key | sha256 of canonical JSON over 11 groups of components (below). The driver and cuda-core versions are left out. A different GPU always misses: a cubin is per compute capability, and that is correct. |
| **Q4** Store | One file per entry, published by temp + fsync + `os.replace`. Every byte is covered by a checksum. A striped `filelock` serialises builds of one key. LRU eviction by mtime under a 1 GiB cap. 9p/drvfs roots are refused, because WSL2 locks don't exclude Windows processes. |
| **Q5** Variants | A five-set `FeatureSet.standard()` across five tiers is 25 kernels: about 21 s cold, serially, for one formula. A small parallel `prewarm` command is worth shipping later (backlog), mainly for after upgrades. |

**Gate verdict: PASS.**

- Warm load in a fresh process: 13–16 ms median per kernel, kernel C in every tier, including
  the `ResourceUsage` lookup; worst sample 21 ms, plus 2 ms for the first launch. The limit was
  100 ms.
- Key correctness: the S4 regression passes. `max_registers=32` and no cap give two entries,
  and each loads its own build: driver register count ≤ 32 against above 32, and the manifest
  matches the driver. A change to any one key component misses; repeating it hits.
- Concurrency: 4 processes asking for one uncached key built it exactly once, left one valid
  entry and no temp files, and all 4 launched with identical results. 20 of 20 rounds passed on
  the GPU, on both Python 3.15.2 and 3.14.0 (and 20 of 20 with the fake backend in CPU CI).
- A simulated version bump misses, never a stale hit: a toolchain version (GPU and fake), the
  codegen version, the Python tag and the format.
- Truncated, bit-flipped, garbage, empty or mis-keyed entries are detected, deleted, rebuilt and
  warned about once, without crashing (GPU and fake; a Hypothesis test flips every byte).

## Kernel ABI: raw pointers, `int64` integers

Mechanism (b) needs a kernel that can be launched without Numba. Numba's array arguments
flatten into its private struct (meminfo, parent, nitems, itemsize, data, shape, strides), so a
loader would have to pack that layout. Instead, a brotkit kernel takes typed device pointers and
rebuilds its arrays:

```python
def kern(c0r, c0i, dx, max_iter, row0, p_f, p_u, h, w, pitch):
    out_f = cuda.carray(p_f, (NLF, h, pitch), F32)   # h, w, pitch: int64
    out_u = cuda.carray(p_u, (NLU, h, pitch), U32)
```

**Go/no-go: passes on public API** (`probe_carray.py`):

- `cuda.carray` is exported from `numba_cuda_mlir.cuda`.
- The PTX entry has one parameter per argument (`.u64` per pointer, `.u32`/`.u64`/`.f32`/`.f64`
  per scalar).
- Numba's own launch and a `cuda.core` launch of the nvJitLink cubin write identical output. That
  holds from a `cuda.core` Buffer and from a pointer taken from `__cuda_array_interface__`.
- The Numba dev path must compile the explicit signature first. A lazily typed dispatcher types
  an int pointer as `int64`, and `carray` doesn't resolve. brotkit always compiles explicitly.

**Cost: same work.** Struct ABI against pointer-int64 ABI. Loop = the escape loop in SASS (the
largest backward branch of the entry). "Addr" counts `LEA`/`IMAD.WIDE`/`IADD3.X`/`SHF`;
"mem" counts loads and stores. Throughput: 3840×2160, max_iter 1000, block 256, alternating,
3 rounds, Giter/s median.

- **Work-equality holds everywhere.** That means the same loop instructions, address ops and
  memory ops, zero spills, and registers in the same 256-register warp allocation.
- **The single exception is f32/F6, and it isn't extra work.** It's in libdevice `sinf`'s
  large-argument reduction (the 2/π table and its local array). There, `x << 1` is
  `IMAD.SHL.U32` in one build and `SHF.L.U32` (which the counter counts) in the other, and two
  `FFMA` become `FADD` + `MOV`. Loads and stores are 7 and 7.
- **The entry functions are 16–40 instructions shorter** with the pointer ABI, because there's
  no struct to unpack.
- **Throughput is informational, per the acceptance rule.** The largest drops (f32/A 0.917,
  dd/C 0.954) come with identical loop instructions and overlapping or noisy ranges (f32/A
  struct runs alone spread 937–1015). f64/A and dd/A go the other way (+5%, +7%).
- **Why `int64`.** A first version passed `h, w, pitch` as `int32`. f32/C then had the same 29
  instructions in a different order and ran **7.8% slower**, in 7 of 7 alternating rounds with
  no overlap. Switching to `int64` gave a third order and −2.4%. `int64` is the rule anyway:
  byte offsets and counts pass 2³¹ for large stills and Buddhabrot histograms.
- **Scheduling sensitivity (a rule for benchmarks).** A short f32 loop moves ±5–8% with
  instruction order alone. An f32 throughput regression needs a SASS diff showing changed
  instructions before it counts as a regression. The template isn't tuned to win a schedule
  back.
- **Plain f32 results can move in the last bits.** In one f32/F6 build ptxas chose `FADD`
  instead of `FFMA` (contraction is on for plain f32, ADR-0006), and total escape counts
  differed by 3.9 × 10⁻⁵ (relative). Every multi-word tier and every other kernel gave
  identical counts.

What the stages are:
- **exec** runs the generated module.
- **frontend** is `mlir_compiler.compile_mlir`: bytecode to Numba IR, typing, lowering to MLIR.
  It is timed outermost only, because it re-enters itself for device callees.
- **MLIR opt** is `mlir_optimization.optimize`, without PTX generation.
- **→ PTX** is MLIR to LLVM 7 / NVVM IR, then libNVVM. sm_86 takes the LLVM-7 bridge.
- **link** is nvJitLink, which runs ptxas, producing the cubin and the log.
- **load** is `ObjectCode.from_cubin` plus `get_kernel`.

The stage timers patch private numba-cuda-mlir functions, for measurement only. The rest of
`compile_ptx` was under 1 ms.

One-time per process (median over all 75 samples):

| | s |
| --- | --- |
| `import numba_cuda_mlir.cuda` | 0.475 (0.457–0.501) |
| `import cuda.core` + device, context and stream | 0.438 (0.420–0.483) |
| Compiler setup on the first compile (MLIR context, libNVVM load, ...) | 0.458 (0.449–0.470) |

- **The frontend dominates.** It is 55–80% of a cold kernel and grows with the number of
  multi-word device-function calls; qf's renormalising adds and multiplies make a qf kernel
  7–10× an f32 one. MLIR, libNVVM and ptxas together are 0.07–0.6 s.
- **The spec's "seconds to compile cold" holds only for qf.** f32 and f64 take 0.2–0.4 s; df64
  and dd take 0.5–1.1 s.
- **The first cold kernel in a fresh notebook costs about 1.4 s more** than the table: the
  imports and compiler setup.

## Q2: mechanisms

### (a) Numba `cache=True`, generated `.py` in its own directory per key

- **What it needs:** a real file. The locator places `__pycache__/<func>-<line>.py315.{nbi,nbc}`
  next to the source and stamps the index with the file's mtime and size. An exec'd string has
  no file and can't be cached. A per-key directory (or `NUMBA_CACHE_DIR` per key) keeps one
  key's entries away from another's.
- **What the key covers** (`MLIRCache._index_key` plus `Cache._index_key`): the signature, the
  CUDA runtime version, the cc, `sha256(co_code)`, a hash of the closure variables, `lto`, `chip`
  and `launch_bounds`. The index file also records `numba_cuda_mlir.__version__` and is
  discarded on a mismatch, so the package version is covered.
- **What it misses, confirmed by test** (`a_keybugs.py`, `a_consts.py`). Process 1 builds X with
  `cache=True`; process 2 asks for Y from the same file; process 3 builds Y with `cache=False`:

  | X → Y | Process 2 | Stale? |
  | --- | --- | --- |
  | `max_registers=32` | hit | **yes** (60 registers; the reference has 32) |
  | `ptxas_options="--maxrregcount=40"` | hit | **yes** (60 against 40) |
  | `lineinfo=True` | hit | **yes** (no `.loc`; the reference has line info) |
  | `opt=False` | hit | **yes** (60 against 73) |
  | `fastmath=True` | hit | not on sm_86, where fastmath changes nothing (S3); it would be on sm_100+ |
  | `launch_bounds=(256, 4)` (control) | miss | no |
  | in-function constant changed, same size and mtime | hit | **yes** (the old constant is written) |
  | constant imported from another module changed | hit | **yes** (Numba's documented limitation) |

- **Load path:** pickle (`.nbi`, `.nbc`) from a user-writable directory. That is no worse than
  any file in the cache, but it is code execution on load, which invariant 3's spirit avoids.
- **Warm load:** 310–340 ms for `dispatcher.compile(sig)` to be served from the cache, on top of
  a 0.72–0.77 s one-time cost (it has to import Numba). See the warm-start table.

As a fallback, (a) works if each key gets its own directory and brotkit's own key decides which
directory to use. Numba's key is then never trusted across options. It is 20× slower to load
than (b), and it keeps Numba and pickle in the warm path.

### (b) brotkit stores the cubin and loads it with `cuda.core` (chosen)

- **Build** (`CudaCacheBackend.build`):
  1. Write the source to `<root>/v1/src/k_<digest>.py` and import it.
  2. `compile_ptx(py_func, signature, cc, fastmath, lineinfo, debug, opt, launch_bounds)`.
  3. One nvJitLink link, with `-maxrregcount` and any ptxas or nvJitLink options. It gives the
     cubin and the verbose log; the PTX salt is a comment, so the cubin is unaffected.
  4. Take the `ResourceUsage` from that log, and the mangled symbol and PTX parameter types
     from the PTX.
  5. Check the parameter types against the signature, which catches ABI drift.
- **Load** (`CudaCacheBackend.load`): `ObjectCode.from_cubin(cubin).get_kernel(symbol)`, with
  `ResourceUsage` rebuilt from the manifest. Numba isn't imported; a GPU test checks that.
- **Launch** (`CudaKernel.launch`): arguments are marshalled by the stored signature.
  - Pointers come from `__cuda_array_interface__` or DLPack through cuda.core's
    `StridedMemoryView`, after checking dtype, contiguity, device accessibility and read-only.
    A `cuda.core` Buffer or an int address is also accepted.
  - Scalars are cast to the parameter's dtype.
  - Every launch goes on the backend's `cuda.core` stream. `StridedMemoryView` with
    `stream_ptr` orders the producer's stream first.
- **Public API only.** That covers `cuda.compile_ptx`, `cuda.carray`, `cuda.bindings.nvjitlink`,
  `cuda.bindings.nvvm` (for versions), `cuda.core.ObjectCode`, `launch`, `LaunchConfig`,
  `StridedMemoryView` and `Stream`. No private numba-cuda-mlir name is used.
- **Fragility.** The parts that could move are `cuda.core`'s launch argument handling
  (NumPy scalars, `np.uintp` for pointers) and `compile_ptx`'s signature handling. Both are
  covered by GPU tests, and the PTX parameter check fails closed.
- **Same results as Numba's own launch:** bit-identical output (`test_cuda_cache.py`).

### (c) Other options in 0.6.0

- `cuda.compile(..., output="cubin")` is unsupported ("Unsupported output type", S4).
- `output="ltoir"` rejects kernels.
- `cuda.core` ships a `utils._program_cache`, but it is for NVRTC programs and is private.
- Nothing does better than (b).

## Q3: the cache key

`brotkit.kernels.cache.key_components` builds this JSON object; the key is
`sha256(canonical JSON)`, where canonical JSON means sorted keys, no whitespace and ASCII:

| Component | Example | Necessary because |
| --- | --- | --- |
| `format` | `1` | The entry layout. A new layout must not parse old files. Also the `v1/` directory. |
| `codegen` | `1` | `CODEGEN_VERSION`: changes the source hash can't see, such as how a backend reads a signature (the ABI). |
| `python` | `cpython-3.15` (`t` if free-threaded) | Numba types bytecode, and bytecode changes between minor versions. The patch version is left out: bytecode doesn't change in a patch release. |
| `backend` | `cuda` | Different binaries; a CPU entry must never load as CUDA. |
| `target` | `sm_86` | A cubin is per compute capability. A different GPU always misses, and that is correct. |
| `entry` | `k_dd_C` | Which function in the source is compiled. It also determines the mangled symbol. |
| `signature` | `["float64", ..., "float32*", "int64"]` | Typing; the ABI and the mangled symbol depend on it. |
| `options` | `{"max_registers": 32}` | Each option changes the build. Tests show stale builds for `max_registers`, `ptxas_options`, `lineinfo` and `opt`, and `launch_bounds` changes registers (62 against 60). Every allowed option has a key test: fastmath, `max_registers`, launch bounds, lineinfo, debug, opt, ptxas options and nvJitLink options. Defaults are dropped, so `{}` and `{"fastmath": false}` are one key. |
| `source_sha256` | | The kernel itself, including every constant: the S2 test where Numba's `co_code` hash missed a changed constant. |
| `toolchain.numba-cuda-mlir` | `0.6.0` | Frontend, MLIR passes and the bundled LLVM-7 bridge. |
| `toolchain.libnvvm` | `2.0 ir 2.0.3.2` | Generates the PTX and bundles libdevice. The library's own version, so a system CTK picked up by `cuda-pathfinder` counts too. |
| `toolchain.libnvjitlink` | `13.5` | Contains ptxas, which allocates registers and schedules (the cubin). |
| `toolchain.nvidia-nvvm`, `nvidia-nvjitlink` | `13.5.37` | Wheel builds within one library minor version. |
| `toolchain.numpy` | `2.5` | NumPy scalar typing and constant folding happen at exec and typing time. Major.minor only, so a patch release doesn't invalidate the cache. Harmless at worst: one rebuild. |

Left out, deliberately:

- **Driver version.** A cubin for sm_86 loads on any driver that runs sm_86, unlike PTX, which
  the driver JIT-compiles and whose accepted ISA version depends on the driver. brotkit stores
  the cubin linked by the wheel's nvJitLink and never asks the driver to JIT. That isn't tested
  across drivers here (there's only one driver on Xenon). It follows from CUDA's compatibility
  rules and from S1's observation that 13.5 wheel output runs on a 13.3 driver. If a driver ever
  rejects a cubin, `load` raises, rather than silently using something stale.
- **`cuda-core` / `cuda-bindings` versions.** They load and launch; they don't produce the
  binary. They are recorded in the manifest (`meta.loader`) for diagnostics.
- **Feature set, precision, formula.** They are all in the generated source, so the source hash
  covers them.

`KernelSpec` accepts only the eight known option names, and the CUDA backend reads options only
through `spec.option()`. An option can't reach the compiler without being in the key; a new
option has to be added to `OPTION_DEFAULTS`, which gives it a key test automatically
(`test_every_option_has_a_variant`).

## Q4: the store

- **Location.** `platformdirs.user_cache_path("brotkit") / "kernels"`, which is
  `~/.cache/brotkit/kernels` on Linux. `BROTKIT_CACHE_DIR` overrides it.
- **Layout.** `v1/<d[:2]>/<d>.bkk` holds the entries, `v1/src/k_<d[:32]>.py` the generated
  source (for tracebacks) and `v1/locks/` the lock files.
- **Entry file.** A preamble: magic `BKKC`, `u32` format, `u64` header length and the header's
  sha256. Then the JSON manifest: digest, key components, metadata (symbol, signature, PTX
  params, `ResourceUsage`, build seconds, loader versions), blob names, sizes and sha256s, and the
  creation time. Then the blobs (cubin, PTX). Entries were 15–207 KB for S4's kernels.
- **Atomic write.** Write a temp file in the same directory, fsync it, then `os.replace`.
  - ext4 (`lock_probe.py`): 3 readers reading a 1 MiB file while it was replaced 300 times got
    23,373 good reads and 0 torn or missing.
  - Renaming a directory onto an existing one fails (`ENOTEMPTY`), which is why entries are
    single files.
- **Last used.** The file's mtime, bumped with `os.utime` on every hit. A hit never rewrites the
  entry and never takes a lock.
- **Cross-process lock.** `filelock` (`fcntl.flock` on POSIX, `msvcrt` on Windows) on one of 256
  stripe files, chosen by the digest's first byte. The stripe files are never deleted, because
  deleting a lock file while another process holds it lets two holders through. The build path
  re-reads the store once it holds the lock, so the losers of a race load the winner's entry.
- **In-process.** One `threading.Lock` per key, so threads asking for different keys don't wait
  for each other.

**Locking results:**

| Test (4 processes × 300 read-modify-writes) | ext4 | `/mnt/c` (9p, drvfs) |
| --- | --- | --- |
| no lock (control) | 360 / 1200: lost updates | 320 / 1200 |
| `fcntl.flock` | 1200 / 1200, 0.52 s | 1200 / 1200, 22.8 s |
| `fcntl.lockf` | 1200 / 1200, 0.56 s | 1200 / 1200, 22.9 s |
| `filelock` | 1200 / 1200, 0.71 s | 1200 / 1200, 66.2 s |
| atomic replace under readers | 0 torn of 23,373 | 0 torn of 680 |
| Windows `msvcrt.locking` while Linux holds `flock` / `lockf` | n/a | **Windows gets the lock at once** |

Under WSL2, locks on `/mnt/c` are local to the Linux VM: they serialise Linux processes but
don't exclude Windows ones. **The cache refuses 9p/drvfs roots** with `CacheLocationError`. The
error names the path and suggests a Linux-side location via `BROTKIT_CACHE_DIR`. The mount type
comes from `/proc/self/mounts`, using the longest matching mount point, with the path's
not-yet-created tail kept. Other network filesystems (NFS, SMB) weren't tested and aren't
refused.

**Corruption.** Each of these deletes the entry, warns once per key per process
(`KernelCacheWarning`) and rebuilds:
- a short file or bad magic;
- the wrong format;
- a header length out of range, or a header checksum, JSON, blob size or blob checksum that
  doesn't match;
- a digest that doesn't match the file name;
- stored key components that differ from the requested ones (never trust a build the cache
  didn't key itself).

Hypothesis covers every truncation point, every single-byte change, and trailing bytes.

**Eviction.** After each build, if the total is over `max_bytes` (default 1 GiB, which is
thousands of entries at these sizes), the least-recently-used entries are deleted, never the one
just built. Temp files more than an hour old are removed too. Eviction takes its own lock and
skips if another process holds it. A deleted entry that another process has just read is
harmless, because that process already has the bytes.

## Q5: variants and prewarm

`FeatureSet.standard()` isn't defined yet. For the estimate it is {none, smooth, smooth+DE,
C, F6}: 5 sets × 5 tiers (f32, df64, f64, dd, qf; qf at `max_registers=128` is one variant, not
two) = **25 kernels per formula per GPU**. Cold costs come from the Q1 table, with "none"
priced as A (an upper bound) and smooth+DE as the mean of A and C:

| Tier | 5 kernels, cold (s) |
| --- | --- |
| f32 | 1.2 |
| df64 | 3.7 |
| f64 | 1.2 |
| dd | 4.1 |
| qf | 10.8 |
| **Total, serial** | **21.0**, plus 1.4 s once |

The compile is CPU-bound in one process, and different keys rarely share a lock stripe, so N
parallel processes cut it to about 21/N s plus the one-time cost per process.

**Recommendation.** Ship a small `brotkit cache prewarm` (backlog, after 1.4), not now.
- Warm loads take 15 ms, and `Precision.AUTO` uses one or two tiers per zoom depth, so the cold
  cost a notebook pays is the handful of kernels it actually renders: 0.2–2.5 s each, once.
- The case for prewarm is upgrades. Any toolchain bump invalidates every entry, so the first
  session after `pip install -U` pays about 21 s per formula for the full preset set.
- A prewarm command should build in parallel processes and default to the presets and the
  current GPU.

## Recommendations and design-doc changes

1. **Adopt mechanism (b)** (ADR-0008): store the cubin, load and launch through `cuda.core`, and
   use Numba only to compile. Landed as `brotkit.kernels.cache` and `CudaCacheBackend`.
2. **The kernel ABI is raw pointers plus `int64`.** The codegen templates (backlog 1.3) emit
   `cuda.carray` views over typed pointers. `CODEGEN_VERSION` is bumped whenever the ABI
   changes.
3. **`KernelCache`** becomes `KernelCache[K](backend, store)` with `get(spec: KernelSpec)`. Its
   slots are store, backend, memory, per-key locks and lock. `KernelSource` wraps a
   `KernelSpec`.
4. **`CompiledKernel.__reduce__`** returns `(KernelCache.get, (spec,))` for the process's cache.
   A worker then gets a disk hit (about 15 ms) instead of a pickled binary.
5. **Variant explosion** (architecture review item 2) is cheaper than the spec assumed. Cold
   compiles are 0.2–2.5 s per kernel, and warm loads take milliseconds. The real cost is the
   first session after an upgrade, which a prewarm command covers.
6. **f32 benchmark rule:** an f32 throughput regression needs a SASS diff before it counts
   (scheduling alone moves short loops ±5–8%).
7. **Free-threaded Python** gets its own key (`3.15t`), but the cache's thread safety hasn't been
   tested there.
