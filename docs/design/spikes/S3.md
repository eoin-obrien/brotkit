# Spike S3: multi-word arithmetic on numba-cuda-mlir

- **Date:** 2026-11-23
- **Machine:** Xenon (WSL2, RTX 3090 Ti, compute capability 8.6, 24 GB VRAM shared with local
  LLM inference)
- **Backlog:** S3 ([#9](https://github.com/eoin-obrien/brotkit/issues/9)), part of the
  [ADR-0005](../decisions.md) backend gate
- **Code:** [`spikes/S3_multiword/`](../../../spikes/S3_multiword/) (throwaway)
- **Outcome:** the original gate (per-kernel fastmath control) **fails** on numba-cuda-mlir
  0.6.0 below sm_100. The maintainer then revised the gate so that multi-word correctness comes
  from codegen rather than compiler flags. The revised gate **passes**, and so do all
  multi-word accuracy checks. Recorded as [ADR-0006](../decisions.md).

## Summary

The spec assumed `fastmath=False` gives multi-word kernels the arithmetic they need: no
contraction, no reassociation, no flush-to-zero. On numba-cuda-mlir 0.6.0 that assumption
fails twice:

1. **`fastmath=True` does nothing below sm_100.**
   - Pre-Blackwell targets compile through a bundled LLVM 7 bridge, and it passes libnvvm only
     `-arch=` and `-opt=`.
   - The PTX, the SASS and the runtime behaviour are identical with the flag on or off.
2. **FMA contraction is always on, and nothing turns it off.** `a*b + c` becomes `fma.rn` with
   `fastmath=False`, on sm_86 and on sm_100. ptxas then fuses un-rounded `mul`/`add` further.

**Revised gate.** Multi-word code never uses bare `+`, `-`, `*`. Every add and multiply is a
libdevice round-to-nearest intrinsic (`dadd_rn`, `dmul_rn`, `fadd_rn`, `fsub_rn`,
`fmul_rn`), and every FMA is an explicit `cuda.fma`. These lower to `add.rn`/`mul.rn`, which
the PTX ISA says are "treated conservatively by the code optimizer", and they reach SASS
unfused on sm_86 and sm_100. With that codegen:

- **Error-free primitives:** zero failures over 10^7 inputs each, in f64 and f32. For
  `two_prod`, that's within an exactly derived domain.
- **Composite ops:** df64 and dd add, mul, sqr and complex mul/sqr stay within 5.04 u of
  mpmath.
- **Deep render:** a dd render at pixel spacing 1e-20 matches mpmath on 4096/4096 pixels.
- **Parity:** GPU results match a CPU run of the same generated source bit for bit.

**What contraction actually does here.** Naive bare-operator code contracts at the instruction
level as predicted. On this toolchain, though, it did **not** push the tested algorithms out of
their accuracy bounds. Its measured effect is non-reproducibility: 20–41% of results differ
in the last bits from the uncontracted computation.

**Throughput on the 3090 Ti:**

| Type | Giter/s | Ratio |
| --- | --- | --- |
| f32 | 1075 | |
| df64 | 178 | 5.5× native f64 |
| f64 | 32.6 | |
| dd | 2.53 | 12.9× slower than f64 |

## Step 1: compiler controls (original gate)

| Control | numba-cuda-mlir API | Result |
| --- | --- | --- |
| Per-kernel fastmath | `cuda.jit(fastmath=True/False)`; `cuda.compile_ptx(fn, sig, fastmath=..., cc=(M, m))` | **Fail below sm_100.** Accepted but has no effect (below) |
| Explicit FMA | `cuda.fma(a, b, c)` (also `cuda.libdevice.fma`, `fmaf`) | Pass: always `fma.rn.f64` / `fma.rn.f32` |
| PTX / SASS | `k.inspect_asm(sig)` (= `inspect_ptx`), `inspect_lto_ptx`, `inspect_sass`, `inspect_llvm`, `inspect_mlir`; `cuda.compile_ptx(..., cc=)` for other architectures | Pass |

| | `fastmath=False` | `fastmath=True` |

The flag reaches MLIR and stops there. (The SASS for this kernel contains `FADD.FTZ` and
`FFMA.RZ/RM/RP`. These belong to the IEEE `div.rn.f32` subroutine and are the same in both
builds. A kernel with no division has plain `FADD` in both.)

### Root cause

- `numba_cuda_mlir/mlir_optimization.py`: `_needs_llvm70_path(cc)` returns true for
  `sm < 100`.
- Kernels for those targets go through `_call_llvm70_capi()`, a ctypes call into
  `_mlir_libs/libMLIRToLLVM70.so`. Its signature takes no option list.
- The only libnvvm option strings in that library are `-arch=` and `-opt=`. The
  `{"ftz": True, "fma": True, "prec_div": False, "prec_sqrt": False}` that `_nvvm_options()`
  builds for fastmath is computed on this path and never passed on.
- The modern path (sm_100+) does pass the options. With `compile_ptx(..., cc=(10, 0))` or
  `(12, 0)`, `fastmath=True` gives `add.ftz.f32`, `fma.rn.ftz.f32` and `div.full.ftz.f32`
  ([`results/upstream_repro.txt`](../../../spikes/S3_multiword/results/upstream_repro.txt)).

### Contraction with fastmath off

- `_nvvm_options()` adds `fma` only when fastmath is on. Otherwise libnvvm's default applies,
  which is `-fma=1` (contract).
- The vendored `numba_cuda.cudadrv.nvvm.compile_ir` has the same shape, so the ADR-0005
  fallback (`numba-cuda` 0.30.4) most likely behaves the same. That wasn't tested here.
- No target option requests `-fma=0`.
- On every architecture, `out = a*b + c` compiles to `fma.rn` with `fastmath=False`.

**The spec's premise for review item 1, that `fastmath=False` means no contraction, doesn't
hold.** So the original gate failed, and the spike stopped and reported.

## The revised gate

The maintainer's revision (2026-11-23): fastmath control was the wrong requirement, and
multi-word correctness must come from codegen. The gate is:

| # | Requirement | Result |
| --- | --- | --- |
| i | Explicit FMA | **Pass.** `cuda.fma` → `fma.rn.{f32,f64}` → `FFMA`/`DFMA` |
| ii | Round-to-nearest, non-contractible add and mul | **Pass.** `cuda.libdevice.dadd_rn`, `dmul_rn`, `fadd_rn`, `fsub_rn`, `fmul_rn` lower to `add.rn` / `mul.rn` / `sub.rn` and reach SASS as separate `DADD`/`DMUL`/`FADD`/`FMUL` on sm_86 and (offline) sm_100. libdevice has no `dsub_rn`, so f64 subtraction is `dadd_rn(x, -y)`; negation is exact |
| iii | No FTZ or reassociation by default on sm_86 | **Pass.** Never observed, with fastmath on or off (subnormal test above, step 2's subnormal groups, step 5) |
| iv | PTX/SASS inspection | **Pass** (table above) |

### Codegen used for every step below

[`gen.py`](../../../spikes/S3_multiword/gen.py) holds one template of device functions written
with ordinary `+ - *`:

- `two_sum`, `fast_two_sum`, `two_prod` (FMA), `split` and `two_prod_dekker` (Veltkamp/Dekker)
- `w_add` (accurate add), `w_mul`, `w_sqr`, `w_mul_dekker`
- `c_mul`, `c_sqr`

For the **rn** variant, an `ast.NodeTransformer` rewrites every float `BinOp` into the `_rn`
intrinsic for that precision. That is how a multi-word printer would emit the code. The
**naive** variant leaves the operators bare. Each variant is written to a real `.py` file
under `gen/` and compiled with `fastmath=False`.

Two codegen pitfalls turned up along the way:

- **Integer × float32 is typed float64.** In generated f32 code, `(x - w // 2) * dx` silently
  promoted the whole "f32" kernel to f64, and the first throughput run measured f32 at f64
  speed. Printers must cast integer index arithmetic to the working dtype (`np.float32(i)`).
  A PTX check that an f32 kernel has no `.f64` ops would catch this.
- **Bare float ops in the kernel body sit next to inlined multi-word code**, for example
  `TWO * m` feeding `w_add`. Contraction can fuse across the inlined boundary, so those
  operations are routed through rewritten helpers too.

## Step 2: error-free primitives (pass)

Each primitive ran on the GPU over 10^7 inputs (12×10^6 for `two_prod`, 8×10^6 for Dekker)
with `fastmath=False` and the rn variant. Every result was checked on the host in exact
rational arithmetic, `Fraction(s) + Fraction(e) == Fraction(a) ∘ Fraction(b)`, spread over a
24-process pool.

**Input groups (as fractions of 10^7):**
- **uniform** (30%): exponents in [−20, 20]
- **mixed magnitudes** (30%): b is a scaled down by 2^gap, gap in [0, 2p+10], past the mantissa
  width
- **near-cancellation** (20%): b = −(a ± j ulp(a)), j ≤ 8
- **subnormal edges** (20%): both inputs subnormal, or a near-min-normal input plus a
  subnormal
- **products only** (+20%): pairs straddling the two_prod domain threshold, plus pairs near
  overflow

`fast_two_sum` inputs are swapped so |a| ≥ |b|, which it requires.

| Primitive | f64: failures / n | f32: failures / n | Subnormal group (f64 / f32) |
| --- | --- | --- | --- |
| `two_sum` | **0** / 10,000,000 | **0** / 10,000,000 | 0 / 2,000,000 each |
| `fast_two_sum` | **0** / 10,000,000 | **0** / 10,000,000 | 0 / 2,000,000 each |
| `two_prod` (FMA), in domain | **0** / 9,182,516 | **0** / 9,186,277 | all out of domain (below) |
| `two_prod` (FMA), out of domain | 2,778,979 inexact / 2,817,484 | 2,783,146 inexact / 2,813,723 | expected-inexact, reported, not failures |
| `two_prod_dekker` (uniform, mixed, cancel) | **0** / 8,000,000 | **0** / 8,000,000 | not tested (split has its own domain) |

`two_sum` and `fast_two_sum` had no exemption, and they are exact on subnormal inputs with no
flush-to-zero. That's consistent with (iii).

### The FMA two_prod domain, derived

Notation:
- p: precision in bits (53 for f64, 24 for f32).
- emin: −1022 for f64, −126 for f32.
- E(x) = ⌊log₂|x|⌋, and q(x) = 2^(max(E(x), emin) − p + 1), the float spacing at x. Every
  float x is an integer multiple of q(x), with |x| < 2^p · q(x).

For finite, nonzero a and b, write π̂ = fl(a·b):

1. a·b is an integer multiple of Q = q(a)·q(b).
2. If π̂ is normal, its spacing is at least 2^(E(a)+E(b)−p+1) ≥ Q, so π̂ is a multiple of Q too.
   Hence e = a·b − π̂ is an integer multiple of Q.
3. Round-to-nearest gives |e| ≤ ulp(π̂)/2 ≤ 2^(p−1)·Q, so e = m·Q with |m| ≤ 2^(p−1). That fits
   in p bits.
4. So e is representable whenever Q is at least the smallest subnormal, 2^(emin−p+1). Then
   `fma(a, b, −π̂)`, which rounds once, returns e exactly.

That gives the sufficient condition:

> **max(E(a), emin) + max(E(b), emin) ≥ emin + p − 1, and fl(a·b) is finite**
> (zero operands are trivially exact)

- **f64:** max(E(a), −1022) + max(E(b), −1022) ≥ **−970**, which is −1022 + 52.
- **f32:** max(E(a), −126) + max(E(b), −126) ≥ **−103**, which is −126 + 23.

The condition also implies |a·b| ≥ 2^(emin+p−1), so π̂ is normal, as step 2 assumed. The rough
"−1022 + 53" bound is one binade stricter than needed. The data shows the exact bound is tight.
On the threshold-straddling group, binned by offset = (exponent sum) − threshold:

| Offset | +3 … 0 | −1 | −2 | −3 | −4 |
| --- | --- | --- | --- | --- | --- |
| f64 inexact rate | 0 | 5.9% | 25.2% | 48.1% | 66.9% |
| f32 inexact rate | 0 | 25.1% | 50.3% | 68.2% | 81.1% |

The condition is sufficient, not necessary. Below the threshold, e is still exact whenever its
low bits happen to be zero, which is why the rate climbs gradually. Inside the domain, the
failure count is zero, as required. In practice, df64 and dd orbit values stay far inside the
domain, so it only matters for extreme magnitudes.

## Step 4: deep orbit test (pass)

**Depth caveat.** The S3 acceptance criterion says "df64 and dd at a 1e-20 coordinate". df64
carries about 48 bits and reaches pixel spacing of only about 1e-13 (spec precision table), so
the spike tests:
- **dd** at pixel spacing **1e-20**
- **df64** at pixel spacing **1e-12**

**Comparison grids.** At 1e-12, plain f64 still works (its limit is also about 1e-13), so for
the df64 case:
- **f32** is the grid that should fail.
- **f64** is an agreement check: df64 should match it everywhere except at boundary pixels.

**Location.** The Misiurewicz point **M(4,1)** (preperiod 4, period 1, |multiplier| ≈ 1.328),
solved with mpmath `findroot` at 100 digits (residual 2e−101):

```
c = -0.101096363845622161025785445738622565463805442826253483876931
  + 0.956286510809141500771096057729977435809833336510529170034314 i
```

Near a Misiurewicz point the set is asymptotically self-similar, so the grid has filaments
crossing it at every depth, with escape counts in the low hundreds.

**Method.**
- 64×64 grid, max_iter 5000, escape when |z|² > 4, tested before each update.
- The GPU tests the hi words of |z|²; the reference tests exactly.
- Pixel c values are computed in mpmath and split into words. The CPU reference iterates the
  exact value of the words the GPU received, so input rounding isn't counted.
- For each mismatch, the reference is recomputed at 120 digits, along with the
  distance estimate in pixels and whether moving c by one unit of the format (u·|c|, in each of
  four directions) changes the 60-digit count.

| Case | Identical to mpmath | Count range | Mismatches |
| --- | --- | --- | --- |
| **dd, spacing 1e-20** | **4096 / 4096 (100%)** | 148–230 (50 distinct) | none |
| **df64, spacing 1e-12** | **4042 / 4096 (98.7%)** | 83–139 (47 distinct) | 54: every one has distance estimate ≤ 0.068 px, every one changes count under a one-unit nudge of c, and the 120-digit count equals the 60-digit count in every case |

For scale, across all pixels the median distance estimate is 3.2 px and the 5th percentile is
about 0.04 px. The df64 mismatches are the pixels lying on filaments, where the count isn't
determined at 48-bit precision, and the reference itself is stable.

| Plain-precision grid | Distinct c values | Distinct counts | Matches multi-word result |
| --- | --- | --- | --- |
| f64 at 1e-20 (dd case): fails | 1 | 1 (uniform) | 0 / 4096 |
| f32 at 1e-12 (df64 case): fails | 1 | 1 (uniform) | 0 / 4096 |
| f64 at 1e-12 (df64 case): agreement check | 4096 | 49 | 4032 / 4096 (98.4%); all 64 differences have distance estimate ≤ 0.133 px. (f64 against mpmath: 4055 / 4096.) |

So df64 is a correct stand-in for f64 at 1e-12. Step 6 shows what that costs.

### 5a: numeric effect of contraction

The plan expected the naive code to fail the exactness and accuracy checks. **It didn't**, on
this toolchain:

| Check (naive variant, `fastmath=False`) | Result |
| --- | --- |
| Step 2 exactness, all primitives including Dekker `two_prod` | 0 failures, same counts as the rn table. `two_prod` in-domain: 0 / 9,182,516 (f64), 0 / 9,186,277 (f32) |
| Step 3 accuracy | max 2.22–4.17 u (dd), 2.38–3.86 u (df64), all ≤ 16 u. Sometimes slightly *better* than rn, because a fused cross term carries extra bits |

**Why.** libnvvm fused only multiplies whose products are already exact (26-bit split halves)
or that feed a sum where an extra rounding doesn't matter. It left the multi-use split
products alone. ptxas fused more aggressively, but the Dekker algorithm survived it here. This
is luck, not a guarantee. It depends on which fusions this compiler version picks, and the
`split` step (`t − (t − a)`) is exactly the kind of expression a later version is free to
fuse.

What contraction measurably breaks is **reproducibility**. The generated template source was
run through a CPU emulation, in pure Python where nothing is contracted: Python floats with
`math.fma` for dd, and NumPy float32 scalars with a correctly rounded f32 FMA for df64. The
GPU results were compared with it bit for bit, over 200,000 inputs per op
([`results/step5_parity.json`](../../../spikes/S3_multiword/results/step5_parity.json)):

| Op | rn: results differing from CPU | naive: results differing from CPU |
| --- | --- | --- |
| dd add | **0** | 0 |
| dd mul | **0** | 40,089 (20.0%) |
| dd sqr | **0** | 50,087 (25.0%) |
| dd complex mul | **0** | 80,351 (40.2%) |
| dd complex sqr | **0** | 82,109 (41.1%) |
| df64 mul / sqr / cmul / csqr | **0** | 40,089 / 49,986 / 80,063 / 81,787 |

The rn GPU kernels are bit-identical to the CPU reference built from the same source. That
gives the multi-word paths an exact CPU/GPU parity test, which spec review item 9 assumed was
impossible.

An identity check (`x*y − x*y == 0`, `Im(z·z̄) == 0` with bare operators) turned out not to be
informative: the compiler folded the repeated product before contraction could apply, and both
builds returned exact zeros. It's in the results file but isn't evidence either way.

### 5c: Blackwell (`compile_ptx(..., cc=(10, 0))`, SASS via ptxas 13.5 and cuobjdump)

| Kernel | Variant | fastmath=False | fastmath=True |
| --- | --- | --- | --- |
| dd mul (Dekker) | rn | 9 `mul.rn`, 6 `add.rn`, 9 `sub.rn`; SASS 9 DMUL, 15 DADD, 0 DFMA | same |
| dd mul (FMA) | rn | 1 `fma.rn.f64`; SASS 1 DFMA | same |
| dd mul (Dekker) | naive | 4 `fma.rn.f64`; SASS 9 DFMA | same |
| df64 mul (FMA) | rn | 1 `fma.rn.f32`; SASS 1 FFMA, 3 FMUL, 5 FADD | **`mul.rn.ftz.f32`, `add.rn.ftz.f32`, `fma.rn.ftz.f32`**; SASS `FADD.FTZ`, `FMUL.FTZ`, `FFMA.FTZ` |

The rn PTX on sm_100 is as clean as on sm_86. One caveat: where fastmath does take effect
(sm_100+), it adds `.ftz` even to the `_rn` intrinsics:

```text
sm_100, fastmath=True, df64 mul        sm_100, fastmath=False
mul.rn.ftz.f32 %r6, %r11, %r13;        mul.rn.f32 %r6, %r11, %r13;
fma.rn.ftz.f32 %r16, %r11, %r13, %r15; fma.rn.f32 %r16, %r11, %r13, %r15;
add.rn.ftz.f32 %r8, %r16, %r19;        add.rn.f32 %r8, %r16, %r19;
```

Flush-to-zero breaks `two_sum` on subnormal inputs: the error term of a subnormal sum flushes
to 0. That's a real mechanism, so **multi-word kernels must still compile with
`fastmath=False`**. The `_rn` intrinsics fix rounding and fusion, not FTZ. f64 has no FTZ mode
in PTX, so dd isn't affected, but the rule stays uniform.

## Step 6: throughput (rough)

z²+c escape time at 3840×2160 with max_iter 1000, on one view all four types can render: the
seahorse valley at −0.743643887037151 + 0.131825904205330i, width 0.05, spacing 1.3e−5.

- **Giter/s** is the sum of escape counts (pixel-iterations actually executed, about
  3.6×10^9) divided by kernel wall time, best of 3 after warm-up.
- Launches are split into row bands of about 0.25 s each (WSL2/WDDM watchdog). Only dd needed
  bands (9 launches).
- f32 and f64 are plain kernels (bare operators, contraction on, as production would run
  them). df64 and dd are rn kernels.

| Type | Time (s) | Giter/s | vs f64 |
| --- | --- | --- | --- |
| f32 | 0.0034 | 1075 | 33× |
| df64 | 0.0203 | 178 | 5.46× |
| f64 | 0.1106 | 32.6 | 1× |
| dd | 1.427 | 2.53 | 0.078× (12.9× slower) |

| Ratio | Value |
| --- | --- |
| f32 / df64 | 6.0 |
| df64 / f64 | **5.5** |
| f64 / dd | 12.9 |
| df64 / dd | 70 |

Caveats:
- The f32 time is only a few milliseconds, so its rate is approximate.
- Mean iterations per pixel were 434.7 and 39.6% of pixels are interior, the same across types
  to within 0.003%.

Implications:
- **df64 beats native f64 by 5.5× on this card**, so `Precision.AUTO` should prefer df64 over
  f64 wherever df64's precision is enough, on cards with a 1:64 FP64 rate.
- dd costs about 13× f64. qf, which was out of scope, runs on the f32 units and would be
  measured against this 2.53 Giter/s in backlog 2.3.

## Other things noticed

- **Device functions can return tuples.** `@cuda.jit(device=True)` functions returning
  tuples work and inline cleanly. The printer's "tuples of scalar locals" plan holds.
- **The CUDA context doesn't survive `fork`.** numba-cuda-mlir raises
  `CudaDriverError: CUDA initialized before forking` in forked workers. Host-side process pools
  that sit next to GPU work need the `forkserver`/`spawn` start method and a `__main__` guard.
- **`compile_ptx` output ends with a NUL** (`'}\n\x00'`). Strip it before handing the PTX to
  `ptxas`.
- **`compile_ptx(..., cc=(10, 0))` compiles for an architecture that isn't installed.** It
  did here, but this machine has a GPU. Whether it works with no GPU present is S4's question.

## Proposed spec changes (applied in this PR)

1. **Architecture review, item 1.** Rewritten: contraction is on by default regardless of
   fastmath, and fastmath is inert below sm_100. The policy becomes: multi-word printers emit
   `_rn` intrinsics plus explicit `cuda.fma`, never bare operators. Multi-word kernels still
   compile with `fastmath=False` (FTZ on sm_100+). fastmath is a performance option for f32
   only.
2. **"What holds up" table.** The multi-word row's caveat is now contraction and FTZ, and it
   notes the bit-exact CPU/GPU parity that rn codegen allows.
3. **Toolchain open questions.** The S3 half of the numba-cuda-mlir gate is resolved (revised
   gate passed). S4 remains.
4. **Precision tiers.** A note that the AUTO tier and the dd-vs-qf benchmark should take
   S3's measured throughput into account (df64 is 5.5× f64 on a 1:64 card).
5. **`Precision.fastmath_allowed` skeleton.** The comment says fastmath is a performance option
   only, currently inert below sm_100.
6. **Review item 9.** Notes the exception: multi-word paths built from rn codegen are
   bit-comparable against a CPU emulation of the same source.
7. **codegen `AGENTS.md` and root `AGENTS.md` invariant 4.** Multi-word code uses `_rn`
   intrinsics and explicit `cuda.fma`, never bare `+ - *`, and compiles with `fastmath=False`.

These are a real deviation from review item 1's mechanism, so they're recorded as ADR-0006.
